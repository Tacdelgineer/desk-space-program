# The kit

Plain browser scripts, no framework. Each file adds one object to `window.DSP`. A mission page loads
them in this order: three.js (from a CDN), `model`, `engine`, `parts`, `shell`, `board`, `ui`, `deck`, `midi`, `tour`, the machines, the mission.
Paths below are inside `labs/` unless they start with `.github`.

## Files

**kit/** (shared by every mission)
- `kit/model.js`: speed math (`calc`, including the crew and where the crew dial runs out), prompt memory from each model's `arch` (`archModel`), real runs (`setRuns`: a matching measured or reported run replaces the estimated speeds, and the weights if it has them; `p.source` and `p.readSource` say which; without one, the nearest run for the same model, another prompt length, crew 1 or another compression, scales the estimate, `p.scaledFrom` for writing and `p.readFrom` for reading; `setPrecisions` gives it the bytes per parameter), the mixture-of-experts rule (`MOE_EFF`, `MOE_STEP_S`: fitted to the Spark's measured and the 5090's reported runs of the same Qwen3.6 file), a graphics card's lookup table left in the PC's memory (`tableOnHost`, `p.hostTableGB`), sized models for the size handle, number formatting, reading the data files. Edit to change how speed is estimated.
- `kit/engine.js`: renderer, lights, post chain, floor, camera shots (a machine can bring its own 2-4), keys, labels on side rails, particles, frame loop. Shot 1 fits a list of boxes into the free screen area (`setFrame({ wide, tall, small, focus, stack })`: the machine, its mug and the console; the machine alone on a phone; `focus` for a screen area a page part hands over with `setArea(fn)`, the guided tour) and keeps them all in the tilt-shift's focus band. `stack` (a 9:16 recording): the machine fills the width at the top, as big as it is alone, and a second camera draws the console across the full width of a band along the bottom (`ScenePass`; the pointer and `toScreen(p, out, owner)` use that camera for the console; the grade pass fades both views into the seam). The pointer layer (`grab`, `block`): anything in the scene you press and drag, with mouse, touch or pen; a press on one never reaches the orbit controls, the scroll wheel turns it. Edit for anything about look or camera that every machine shares.
- `kit/parts.js`: rounded box, materials, board texture, and one builder per part (tiles, memory, caps, SSD, network chip, ports or a `portRow` from a list, heat pipe, cooler, fan). Edit to add a part; builders take coordinates from the machine file.
- `kit/board.js`: what every machine does as the simulation runs: bus lanes (one per 32 bits) with flowing data, memory cells (a model's lookup table in amber; in live mode the real memory in use), one prompt-memory group per request, GPU blocks lit in proportion to the math used, the maxed-out marker. Edit to change how all machines light up.
- `kit/shell.js`: the outside of a machine and the moment it opens. `block` (a lid from an outline, with round fan holes), `band` (a trim line), `plate` (the printed spec plate: name, memory, bandwidth), `mug` (the same 82 x 95 mm mug at a machine's real scale), `rig` (k from 0 to 1: the lid pops, rises and stays hanging high above the machine, tipped back, where the top of the frame shows it and it can be dragged back down (`park`); the cooler rises from where it sits inside into the exploded view). Generic: the machine file decides the shapes.
- `kit/deck.js`: the Mission Control console in front of the machine: five machine pads, the model-size fader with detents at the presets, the crew jog wheel (one lit block per request, red past where the GPU maxes out, magenta past full memory), the compression lever, three prompt switches, the launch switch under a flip-up cover, and on the meter bridge two needle gauges, the 7-segment tokens/s display and the LID key switch (open / closed). The layout (`L` at the top of `build`) gives every printed label a strip in front of or right of its control: the overview camera looks down at about 50 degrees to the deck from a little to the right, so anything tall hides the deck behind it and to its left (about 0.8 of its height). The words print on a transparent layer lifted off the paper (`inkMat`), and they shrink to fit their strip when a wide fallback font is in. Springs give the detents and presses their feel. `build(o)` takes the lists and handlers, `set()` shows the selection, `setLid()` turns the key, `show()` the live numbers, `arm()` throws the launch switch, `drive()` takes a MIDI message, `where(id)` finds a control on screen. Edit for the console's layout and feel.
- `kit/midi.js`: Web MIDI (Chrome, Edge): a MIDI button that asks for access only when pressed (or connects quietly when the browser already allowed it), learn mode (touch a console control, move a hardware knob, fader or pad), mappings kept in localStorage. No Web MIDI: the button stays hidden.
- `kit/tour.js`: the guided tour, a story in acts, slowed down, so a plain screen recording of the page is a finished video: the step card (act, title, 3-4 sentences, "Think of it as...", three number chips tagged measured / reported / estimated, a "break it" button, the real-data line), the trip map across the top (SSD, memory, bus, GPU, port, you) with the clock ("4.20 s since you hit enter, slowed 20x"), a one-line caption, the scrubber with the acts, 1/2x 1x 2x, play/pause, the arrow keys, Esc, and the "What if..." panel (dense or MoE, machine, crew 1 or 32, 4- or 16-bit; it changes the current step only). `start(data, lab, { autoplay })`: autoplay plays the whole tour in about 30 s and ends, with the card trimmed to the title and one big number (the step's `big` chip) and What if hidden, so a recording carries only that and the caption (in 16:9 the mission also lifts the open lid right out of the frame); a tall window (9:16) gets the card on top, the machine in the middle, the caption at the bottom. It hands the free screen area to the engine (`setArea`), owns the clock and asks the lab for every number (`lab.metric`), so the words hold `{k}` placeholders, never typed numbers. `outline()` gives the running tour as text with every number filled in and tagged, and each step's start and end in an autoplay recording (`tools/tour-text.mjs` prints it). Edit for how a tour looks and plays; a tour's content is a data file.
- `kit/ui.js`: pills, race panel (one row per machine, tagged measured or reported when a real run is behind it), toast, dialogs, hide-interface, the controls bar (on a desktop it waits below the screen: B or the Controls bar link pins it, Tab shows it). Edit for interface behaviour, not for wording.
- `kit/themes/screenprint.css`: the whole retro screenprint look, one file. Swap it to reskin.

**tours/** (one JSON file per tour, read by kit/tour.js through the mission's lab)
- `tours/life.json`: "The life of one answer", the main tour: Qwen3.8 27B on the Spark, the question prompt, 12 steps in four acts (Load, Read, Write, Answer). `tours/ep1.json`, `tours/ep3.json`, `tours/ep4.json`: episodes 1, 3 and 4 of EPISODES.md, 4-5 steps each. A step: `act`, `title`, `text` (3-4 sentences), `metaphor`, `chips` ([{ k, label }] plus overrides: `m` a machine, `model`, `bits`, `prompt`, `crew`), `breakIt` ({ label, set: {state}, caption }), `caption` (12 words at most), `cam` (shot 1-4), `trip` (the stops lit), `state` ({ t: seconds since enter, negative while loading; slow; and any of machine, model, bits, prompt, crew }), `report: true` for the five-machine table, `weight` (share of the autoplay time; the tour's `autoplayS` sets the total, 30 s by default), `big` (the chip autoplay shows big, 0 by default). Numbers only as `{k}`, `{k:machine}` or `{k:model}`; the metrics are listed in `metric()` in mission.js. Open one with `?tour=life` (`&autoplay=1` to record). A tour is registered by one `<script type="application/json" id="tour-<id>">` tag in the mission's index.html; the mission finds every `tour-*` script.

**machines/** (where the parts sit, and how the machine lights up)
- `machines/spark.js`, `machines/rtx5090.js`, `machines/m3ultra.js`, `machines/strixhalo.js`, `machines/rtxpro6000.js`: where each machine's parts sit, its bus lanes, labels, close-up shots. Each builds into its own group (so it can sink into the stand) and hands its parts to `board.lightUp`. Each also builds its closed shell (a hood over a desktop box, a fan cover over a card; stylized, no logos), the spec plate and the mug at its real scale, keeps its cooler in a group that sits on the chip while closed, and returns `shell: { rig, grab, plate, hint, what }`. The 5090's plate and fin block move separately and its heat pipes are laid again between them as they go. Copy one to start another machine, then add it to `data/machines.json`, the mission's script list and `WORDS` in `mission.js`; the switcher, the race and the console's pads pick it up from there. The Strix Halo (AMD Ryzen AI Max+ 395, 128 GB) builds its turned SSD in a sub-group and its case from its own materials (graphite, a hex-perforated sheet cut with an alpha map). The RTX Pro 6000 is a double flow-through card: a compact main board, fin stacks at both ends, PCIe and display boards on their own, 188 of 192 SM blocks (`tiles` with `skip`), 16 memory spots of 6 cells with the second chip of each pair under the board.

**data/** (every number is `{ "value": n, "source": "measured" | "reported" | "estimated" | "config" | "chosen" }`, with `link` and `note` where there is one)
- `data/machines.json`: memory, reserve, bandwidth, TFLOPS per machine. The Strix Halo's are reported with their links (AMD's spec pages, a Linux setup guide for the 120 GB its GPU may map) and it lists the specs its interior is drawn from (bus width, compute units, NPU, power, ports). Edit when a spec is checked or measured.
- `data/models.json`: the five models (Gemma 4 E4B, Qwen3.6 35B-A3B, Qwen3.8 27B, Qwen3.8-Flash-Next, Qwen3.8-Max): total, active and table parameters and `arch` (layers that keep a cache, KV heads, head size, sliding windows, linear-attention state), all from each model's config and checkpoint; the 4-bit GGUF the Spark benchmark runs; compression levels (bytes per parameter), the prompt lengths, and the size handle's range and scaling. The `about` field says how each number was counted.
- `data/measured/spark.json`: written by the live benchmark (`live/`), never by hand. Speeds, file sizes, power, temperature and GPU clock for each model at 4-bit with the 300- and 8,000-token prompts.
- `data/reported/pro6000.json`: the one published llama.cpp run of a lab model on the RTX Pro 6000 (Flash-Next, a 22,695-token prompt standing for the codebase prompt; `about` lists the near misses).
- `data/reported/strix.json`: other people's published llama.cpp runs on the Strix Halo, one per model and prompt, each with its link and which point of the source it takes (their prompts are 2,048 tokens: depth 0 stands for the question, depth 8,192 for the document). `about` gives the rules they were picked by. Same shape as a measured file, `source: "reported"`.
- `data/reported/rtx5090.json`: published llama-bench runs on the RTX 5090 (witcheer's rtx-5090-benchmarks): Qwen3.8 27B (Q4_K_M) and Qwen3.6 35B MoE (the Spark's UD-Q4_K_M file); the question takes pp512 and tg128, the document pp8192 (reading only, its writing is scaled).
- `data/reported/mac.json`: published MLX runs on the Mac Studio M3 Ultra (Rapid-MLX's methods page: Qwen3.8 27B without its MTP head, Flash-Next; one oMLX community run: Qwen3.6 35B MoE, document only). `about` says which point of each source stands for which prompt.
- `data/missions.json`: the list on the hub page. Set `status` to `live` and add `dir` when a mission ships.

**missions/01-liftoff/** (one folder per mission)
- `index.html`: the page markup and the words; pulls the pieces together. Edit for copy and layout.
- `mission.js` (section 7 is the guided tour's lab: state, timeline, the metrics behind every chip, the real-data line, the Mission Report rows; the console slides away while a tour runs): the choices, machine switching (the old machine closes its lid, sinks, the new one rises), the case (starts closed; dragging the lid up, a tap on it, O, the console's LID key or a launch opens it; the open lid hangs above the machine and dragging it back down, a tap, O or the key closes it), size handle, crew dial, the console wired to the same handlers as the bar, URL presets (list at its top; `open=0|1`), the simulation phases and the live text. Edit for what the mission does.

**hub/**
- `hub/index.html`: template for the hub page. The build fills in the mission list.

**Build and checks**
- `build.mjs`: `node labs/build.mjs` writes `dist/` (gitignored): `dist/index.html` and `dist/<mission>/index.html`, each one file, plus `assets/` (copied from `labs/assets/`). Every page gets the link-preview tags (og:image and twitter:image on `assets/preview.png`) unless it names its own.
- `assets/preview.png`: the 1200 x 630 link-preview image, made by `scripts/preview.mjs` (a render of the open Spark beside the title).
- `tools/shoot.mjs`: deterministic screenshots of a page or a preset (`page.html?machine=mac&crew=16`) and a pixel compare. Needs `npm i --no-save playwright` once. `SHOOT_GPU=1` (fast), `SHOOT_SIZE=1080x1920`, `SHOOT_UI=1`, `SHOOT_PHASE=reading` (halfway through reading; use `prompt=doc`), `SHOOT_PHASE=midwrite` (halfway through the answer, for fast machines), `SHOOT_CASE=closed|opening|open` (no launch), `SHOOT_EVAL='js'` (run just before the picture, e.g. `__lab.deck.pose({ hover: 'fader', cover: true })`).
- `tools/tour-text.mjs`: `node labs/tools/tour-text.mjs ep4` prints a tour with every number filled in and tagged, and each step's place in the autoplay (`--json` for the outline). Proofread new tours with it.
- `../scripts/check.mjs` (/check, also the pre-push hook in `../.githooks/`): builds, pictures the key states at 1920x1080 and 1080x1920 on `out/check/contact-sheet.png`, and fails on hostnames, IP addresses, ports, local paths, user names or tokens in `dist/`, a page error, a blank picture or a page without its link preview.
- `tools/report.mjs`: an episode's Mission Report numbers for the five machines from the data files, with the source of every input; measured numbers are marked (meas.), reported ones (rep.), scaled ones (est. from meas.) or (est. from rep.), writing and reading separately when they differ.
- `../live/`: live mode on the Spark (`node live/bridge.mjs`): serves `dist/`, runs real models through llama.cpp, streams memory, power and temperature, and the benchmark. See `live/README.md`.
- `_baseline/`: the three reference screenshots (software render, the default page: Spark, Qwen3.8 27B, with the measured speeds of 2026-09-30, opened and launched, the console in front, the lid hanging above; regenerated 2026-09-30 in Session G for the console's new layout) and the original single-file page. Regenerate them after a new benchmark: the measured speed decides how far the answer has got in each shot.
- `../.github/workflows/pages.yml`: on push to `main`, builds and deploys `dist/` to GitHub Pages.

## Everyday commands

```
node labs/build.mjs                                  # then open dist/01-liftoff/index.html
node labs/tools/shoot.mjs dist/01-liftoff/index.html /tmp/shots
node labs/tools/shoot.mjs --compare labs/_baseline /tmp/shots
```

A source page (`missions/01-liftoff/index.html`) fetches its data files, so serve `labs/` over http to open it
directly. The built page has everything inline and opens from a file.

## Gotchas

- Headless Chrome on the DGX Spark: Playwright's default headless shell only has software GL. Full Chromium (`channel: 'chromium'`) with `--use-angle=gles-egl` renders on the GB10 (`SHOOT_GPU=1`). ANGLE on Vulkan draws black there: NVIDIA's driver fails the shadow-pass pipelines, so the engine turns shadows off when it sees NVIDIA + Vulkan. The baseline stays software-rendered (about 20 s per shot).
- `shoot.mjs` blocks the web fonts on purpose: board text is drawn before they load, so it would flip between two fonts.
- The theme sets `overflow:hidden` on the body for the full-screen lab. A page that scrolls (the hub) has to undo that.
- `new THREE.Color()` is white, not black: reset an emissive with `new T.Color(0x000000)`.
- The key light is tuned for dark boards. Anything cream, yellow or red needs a darker albedo than its ink (the deck print is multiplied by 0x6e6a62), and a clearcoat on a surface that faces up mirrors the studio's bright ceiling and prints white.
- A printed plane on an extruded body has to sit outside the body's bevel, or it vanishes inside it. A body right under a print casts from its back faces (`shadowSide`), or the print gets shadow stripes.
